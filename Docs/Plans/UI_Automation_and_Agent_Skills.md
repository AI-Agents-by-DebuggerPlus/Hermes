# План: управление UI (мышь, клавиатура) и «навыки» агента

## 1. Цель

Дать ассистенту (Hermes в WSL + клиент Hermes.Wpf) возможность **управлять рабочим столом Windows**: курсор, клики, правая кнопка, фокус полей ввода, набор текста, Enter — при этом избежать случайного или скрытого вредоносного поведения.

## 2. Может ли агент «сам создавать скилы»?

- **Внутри LLM** «скилл» — это текст инструкции или вызов уже известного инструмента. Модель не получает магическую новую способность без **исполнителя** на машине (код, процесс, API ОС).
- **Полезный подход:** агент генерирует **скрипты или конфигурации** (PowerShell, Python, AutoHotkey) под конкретную задачу, а вы запускаете их вручную или через явно разрешённый раннер — тогда «сам создал скилл» означает «сам написал автоматизацию», а не «сам обошёл песочницу».
- **Небезопасный подход:** без ограничений вызывать `SendInput` / синтетические события из любого ответа модели — высокий риск ошибок и злоупотреблений.

**Вывод:** просить модель «придумать скилл» имеет смысл для **логики и сценариев**; для **ввода в ОС** нужен **внешний доверенный инструмент** с политикой доступа.

## 3. Варианты реализации на Windows

| Подход | Плюсы | Минусы |
|--------|--------|--------|
| **Win32 `SendInput`** (или обёртка InputSimulator) из малого .NET helper | Низкая задержка, полный контроль API | Нужны права, защита от произвольных вызовов, UAC/антивирус |
| **UI Automation (UIA)** | Семантический поиск элементов, стабильнее для своих WPF-приложений | Сложнее для чужих UI; не заменяет «мышь в игре» |
| **PowerShell + WASP / .NET** | Быстрые прототипы | Те же риски безопасности, хрупкость |
| **Существующие инструменты** (AutoHotkey, SikuliX, Playwright для веба) | Проверенные сценарии | Отдельная установка, версии, путь в PATH |
| **Отдельный «robot» процесс** с IPC от Hermes | Один канал аудита, можно kill по таймауту | Два компонента в релизе |

Рекомендация для Hermes: **отдельный узкий исполнитель** (например `Hermes.UiRobot.exe` или именованный pipe + подписанные команды: `Move`, `Click`, `Type`, `Key`), который:

1. Запускается только при явной настройке пользователя («разрешить UI-робота»).
2. Принимает **ограниченный набор команд** с лимитами (частота, область экрана опционально).
3. Пишет **журнал** всех действий в файл, видимый пользователю.

Hermes в WSL вызывает его через **проброс в Windows** (`/mnt/c/.../Hermes.UiRobot.exe` или `powershell.exe -File ...`) только когда пользователь включил опцию и подтвердил риск.

## 4. Что уже сделано в Hermes.Wpf

- Вкладка **«Навыки»**: карточки возможностей + smoke-тест сдвига курсора (при opt-in в Settings).
- **Курсор мыши:** библиотека `Hermes.DesktopInteraction` (`SetCursorPos`, `mouse_event` для ЛКМ/ПКМ), сервис `MouseSkillService` в Wpf, консоль **`Hermes.MouseBridge`** для вызова из скриптов и WSL (`move`, `moveby`, `click`). Клавиатура и полноценный UI Automation — по-прежнему вне текущей реализации.

## 5. Что требует уточнений (следующий этап)

1. **Доверие и границы:** только текущий монитор / запрет вводу паролей / пауза по горячей клавише.
2. **Канал из WSL:** запуск `.exe` на стороне Windows из сессии Hermes (путь, quoting, кодировка).
3. **Совместимость с удалённым рабочим столом и масштабированием DPI** (per-monitor DPI).
4. **Юридическое/корпоративное:** допустимость синтетического ввода на рабочих ПК.

После ответов на эти пункты можно спроектировать `IUiAutomationGateway` + один исполнитель и точку вызова из существующего пайплайна Hermes (tool / slash-command), не смешивая с обычным текстом чата без маркера.
