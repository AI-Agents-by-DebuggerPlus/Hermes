# Скринер плотностей для Hermes — архитектура

Разложу задачу на слои, вписав их в уже существующую архитектуру Hermes (WPF + WSL CLI, file-based IPC, dual execution paths, multi-layer risk control).

## 1. Что считать "плотностью"

Плотность — это кластер крупного объёма в стакане (order book wall) или в объёмном профиле, от которого статистически чаще происходит отскок. Два источника:

- **Стакан (order book)** — снапшот + дифф через WebSocket, агрегация объёма по ценовым бакетам (bucket size зависит от инструмента, напр. 0.1% от цены).
- **Volume Profile / Footprint** — накопленный объём сделок (не заявок) по ценовым уровням за период (POC, HVN/LVN зоны). Это устойчивее к спуфингу, чем голый стакан.

Разумно детектировать оба и объединять: "сильная плотность" = совпадение стенки в стакане с HVN на профиле.

## 2. Источники данных Binance

- `GET /api/v3/depth` — снапшот стакана (лимит до 5000 уровней) для инициализации.
- `wss://stream.binance.com/ws/<symbol>@depth@100ms` — дифф-обновления стакана в реальном времени.
- `wss://stream.binance.com/ws/<symbol>@aggTrade` — сделки для построения volume profile / footprint.
- `GET /api/v3/klines` — для контекста (текущий тренд, ATR для нормализации плотности).

Держать локальный "живой" ордербук (rebuild by lastUpdateId + diff apply, стандартная схема Binance) — это должен делать отдельный процесс, не UI.

## 3. Слои реализации (под ваш стек)

**Python-сервис (data + detection)**
- Поддерживает live-стакан и трейд-ленту per symbol.
- Считает плотности: bucket-агрегация, порог по перцентилю/стандартному отклонению от среднего объёма бакета, скользящее окно для устойчивости к спуфинг-миганию (плотность должна "прожить" N секунд, иначе игнорим).
- На выходе — структура `DensityLevel { symbol, price, side(bid/ask), volume, strength(0-1), source(orderbook/profile/both), firstSeen, lastSeen }`.
- Публикует состояние: в файл (JSON snapshot, как у остальных модулей Hermes через file-based IPC) и/или в таблицу Supabase — тогда WPF и агент читают из одного места, и заодно есть история для бэктеста.

**WPF-модуль (визуализация)**
- Ценовая лестница (DOM-style) с heatmap: интенсивность цвета = сила плотности, ширина полосы = объём.
- Отдельная дорожка volume profile сбоку (гистограмма по ценам).
- Живое подсвечивание momentum: когда цена подходит к плотности — визуальный алерт (это же событие уходит агенту).

**Данные для агента Hermes**
- Раз Hermes уже общается через file-based IPC — самый органичный вариант: `HermesAgentService` получает новый provider, который читает JSON/Supabase snapshot плотностей и отдаёт агенту через существующий канал (как отдельный "skill"/контекст, аналогично тому, как у вас организованы роли и skill registries).
- Формат для агента должен быть компактным и с семантикой уже готовой для решения: не сырой стакан, а список актуальных `DensityLevel` рядом с текущей ценой + дистанция до каждого в % и в ATR.

## 4. Алгоритмическая отработка отскоков

Отдельный стратегийный модуль (вписывается в уже существующий dual execution path и risk control):

1. **Триггер входа**: цена подходит к плотности на X% (или X ATR), при этом импульс подхода замедляется (например, серия свечей с уменьшающимся range) — фильтр от "пробойных" случаев.
2. **Подтверждение**: плотность не "съедена" (объём на уровне не начал резко уменьшаться — признак, что стенку едят, а не защищают).
3. **Вход**: лимит/маркет по текущим правилам риска Hermes (используя уже найденные вами баги — market-order risk bypass, UsedMargin, LiquidationPrice — это критично не воспроизвести и здесь).
4. **Стоп**: за уровнем плотности (плюс буфер на шум).
5. **Тейк**: до следующей значимой плотности на встречной стороне, либо фиксированный R-multiple.
6. **Инвалидация**: если плотность "съедена" (объём упал ниже порога) — либо закрыть, либо перевести в трейлинг.
